# Standalone ChatGPT Site

A Site is a hosted visual application, not the same surface as an MCP tool inside conversation. Build a focused scenario experience rather than every Android screen.

## Verified platform constraints

Current official Sites documentation describes a public-beta deployment workflow, supported web protocols, secrets management and hosting resources. This audit did not verify that its runtime can execute the approved Python engine. Do not solve that uncertainty with a TypeScript financial rewrite: use engine-generated presets, or an authorized Python HTTPS backend after runtime/privacy qualification.

Sites documentation states no data/inference residency support at launch and includes platform analytics. Do not claim no telemetry merely because no custom analytics SDK is added. Keep financial values out of URLs, titles and analytics events. Audience access is not the same as financial-data authorization. Every deployed URL is a live surface; review versions before publishing. Secrets belong in protected environment settings, never prompts/client bundles.

Current July23,2026 Sites terms restrict initiating/executing/facilitating financial transactions outside their specified e-commerce exception. MonteCarlo's Site is calculation-only, with no bank transfer or bill-payment execution. Hypothetical scenarios are labeled hypothetical, not authorization from a bank/payee. Recheck terms before launch and obtain appropriate legal/privacy review; this plan does not certify acceptance/compliance.

## Stage1 — synthetic demo, recommended

Use several synthetic households and exact engine-generated result bundles: steady income, late/smaller paycheck, bill pressure, pending hold and card payment. Visible synthetic-data label. Purchase/delay controls select precomputed results; arbitrary inputs are disabled until a conforming live backend exists. Never interpolate a chart into an uncomputed answer. No sign-up, real bank connection, ledger upload or persistent finance storage.

This validates hierarchy/accessibility/terminology without financial-data collection. A static result viewer is honest when backend/runtime/rights are not yet ready.

## Stage2 — privacy-gated ephemeral scenarios

After D01 and P11, collect only normalized opening position, relevant commitments/income, account/horizon/reserves and explained assumptions. Prefer minimal scenario exports produced locally to full ledgers. Show exactly what will be transmitted and to which service before submission.

Use a separate approved Python backend over HTTPS when needed. Frontend validates/presents, not computes finance. Use in-memory session state; no financial localStorage/IndexedDB/D1/R2/server ledger by default. Clearing session data is available, with honest infrastructure/provider retention disclosure. Storage availability is not a reason to use it.

Data flow is browser→Site infrastructure→named calculation provider; an optional model explanation is a separate opted-in destination. Review logging, analytics, support access, regions, retention, deletion and model controls before real data. Do not call a remote calculation local-only; CLI/Android remain the local-first alternatives.

## Persistent authenticated finance — postponed

Requires a separate owner decision, tenant/auth/recovery design, data inventory, retention/deletion/export/backup, incident support, privacy notice and jurisdictional review. ChatGPT audience authentication is not a complete financial authorization model. Residency needs unsupported by Sites block that deployment or require a separately qualified hosting product. No silent upgrade of ephemeral sessions into stored ledgers.

## Visual priorities

Overview shows qualified modeled headroom, separate shortfall, account/horizon and reconciliation/coverage above the number. Unknown data suppresses a definitive safe recommendation. Timeline shows opening, daily closes, pending holds and scheduled events; pressure-window detail names the crossing obligation and assumptions. A combined balance cannot conceal checking risk.

Risk view uses returned p10/p50/p90 daily-close points, with separately named minimum/ending summaries, any-negative count/runs, model/seed and assumptions. Explain pointwise bands versus whole trajectories. Sparse history is visible, not disguised as personalized certainty.

Scenario builder starts with purchase, delayed/smaller income and bill-date change. Compare baseline/proposal on one snapshot and common draws; show computed deltas and changed assumptions. Rescheduling is hypothetical, not payee agreement. Debt payoff appears after debt/cash guard conformance; category volatility after coverage-aware calibration. CRUD, backup management and full settings stay native/CLI initially.

All money remains string cents until display formatting. Chart geometry can use scaled floating coordinates but never feed engine results. Provide accessible tables, keyboard navigation, non-color risk labels and mobile layouts. Failure cannot leave old results marked current. Test unreconciled/negative/no-income/no-history/invalid/duplicate/expired/failed cases.

First-release done: a user can understand one synthetic tight window and compare one hypothetical purchase with engine-backed results. Persistent finance and actual payment execution are outside scope.
